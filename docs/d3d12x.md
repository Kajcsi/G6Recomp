# D3D12.X

What the console's variant of D3D12 looks like from the title's side, which is what
`runtime/gpu` will have to present at M3. Prose findings only; see `CLAUDE.md`. Findings that
other projects report are listed in [related-work.md](related-work.md); this page holds what we
have checked on our own files.

## Our device

**Built** for the first step of M3, where run 8 stopped ([boot.md](boot.md), "Our runs"), and
tested by `test_device` on a WARP device. In run 9 the title passes no adapter and asks for
`ID3D12Device11`.

* `D3D12XboxCreateDevice(adapter, parameters, riid, out)` in `runtime/imports/d3d12_xs` logs its
  arguments, with the parameter block's first 24 words at debug level. It asks `runtime/gpu` for
  a device, which creates a PC device on the default adapter at feature level 12.0 and hands out
  its proxy as `riid`. The title's adapter argument is logged and not used.
* The proxy is the object the title holds. Its first word points at a table of 192 slots, more
  than the highest slot seen (133). The table ends at a page boundary, before a page with no
  access, so a slot past it faults at a clear address instead of jumping through whatever
  follows. The PC device sits at +8, and the byte at +0x18 is 1, so descriptor copies go through
  slot 24 ("Descriptor copies", below).
* Slots 3 to 42 are the base `ID3D12Device` methods, which keep their PC order on the console
  (Leonida's run and the upscaler's slots 15 and 24). Each is a 13-byte thunk, written once at
  start-up, that swaps `this` for the PC device and jumps through the same slot of its table.
  Arguments on the stack and the return value pass straight through, and the thunk needs no
  unwind data, since it never moves the stack.
* The proxy handles these slots itself:
  * IUnknown (0 to 2). `QueryInterface` answers `IUnknown`, `ID3D12Object`, and the
    `ID3D12Device` interfaces the PC device has.
  * Slots 25 and 26 return structures, and the title passes the return buffer first and the
    device second ([boot.md](boot.md), "D3D12 device calls that differ from the PC"). Both forms
    are taken, and the device is whichever argument is a live proxy.
  * Slots 8, 9 and 12 make command queues, allocators and lists, and slots 48 and 73 are the
    console's own forms of the queue and list calls ("Command queues and lists", below).
  * Slots 78 to 80 are the frame clock ("The frame clock", below).
  * Slot 43, `GetAdapterLuid`, returns 8 bytes, which in the title's form would come back in
    `rax`. Until a call shows the form, it is handled like the slots below.
  * Every other slot from 44 up, where the console's table differs from the PC's, logs its first
    call, with the caller and the first three arguments, and returns `E_NOTIMPL`.
* The tables of the device, queue and list proxies are built the same way, by `ProxyTable` in
  `runtime/gpu/proxy.h`.
* Next, in the order the title calls them: slot 133 (run 13), then the descriptor heap's slots
  9 and 10, which Leonida's run met.

## Command queues and lists

**Built** after run 9 stopped at device slots 48 and 73 ([boot.md](boot.md), "Our runs"), and
tested by `test_device` on a WARP device, including a timestamp query recorded through the
console's list slots, run on a queue proxy and read back.

* Queues come from slot 8 with the PC's arguments or slot 48 with the console's: a 32-byte
  description whose first 16 bytes are the PC's `D3D12_COMMAND_QUEUE_DESC` (type, priority,
  flags, node mask) and whose last four words are the console's own and are logged. In runs 10
  and 11 the title makes four compute queues there, with flags 1, 2, 3 and 0, and the same four
  words each time (`1, 0, 0x40000000, 1`).
* The console's description has values the PC refuses with `E_INVALIDARG`, so both slots map it:
  * flags keep only `DISABLE_GPU_TIMEOUT` (1); other bits are dropped and logged, as xcl and
    Leonida do;
  * type `0x10` is the console's copy engine, the PC's `COPY` type (xcl), which also applies to
    allocators (slot 9) and lists;
  * a priority the PC doesn't have becomes `NORMAL`, and any node mask becomes the first node.
* Lists come from slot 12 with the PC's arguments or slot 73 with the console's: a 16-byte
  description with the type at +0 and the node mask at +8 (run 10: `0, 2, 1, 0`), then the
  allocator, the initial pipeline state, and the interface ID. The title asks for
  `c3827890-4024-474c-98cf-645b51dc4874`, which the PC SDK doesn't have; the list proxy answers
  it along with the PC's list interfaces.
* A queue proxy keeps the PC queue at +8 and a reference to the device proxy, which its
  `GetDevice` hands out. Slots 0 to 13 keep the PC's order and are forwarded, except slot 10,
  `ExecuteCommandLists`, which hands the PC queue the lists behind the proxies and leaves out
  anything else, with a log line. From slot 14 on, the console has two queue layouts
  ("Reported by other projects", below), so those slots stay logged until a call shows which one
  the title has.
* A list proxy is 0x5A0 bytes: the PC list at +8, then zeroed bytes up to +0x580 for the
  title's own fields ("Command lists write records inline", below), which reach +0x564. Since
  the write pointer and the ends start at zero, every record goes through a method. Slots 0 to 26
  keep the PC's order and are forwarded, 32 to 59 are the PC's 28 to 55, and 61 is
  `ExecuteIndirect`. Slots 27 to 31, 60, and everything from 62 on are logged.
* Next: list slots 131 and 132, which the title calls right after its first list, with
  `0xC3C0, 0x80020000` and `0x700000` (runs 10 and 11).

## The frame clock

**Built** after run 11 stopped at device slots 78 and 79 ([boot.md](boot.md), "Our runs"), and
tested by `test_device`: origins a frame apart with tokens of their own, a later event, the
title's own event signalled with the origin, timeouts, and unscheduling.

A console title paces its frames by a clock the device runs, not by a swap chain. The slot
numbers, names, and argument shapes are as xcl and Leonida report them; runs 12 and 13 show the
first two calls.

* Slot 78, `SetFrameIntervalX(output, length in µs, periodicity, flags)`, sets the frame length.
  The title asks for 33,333 µs, with periodicity 3, no output and no flags: 30 frames a second.
  A length of 0 stops the clock.
* Slot 79, `ScheduleFrameEventX(type, offset in µs, handle block, flags)`, puts an event at an
  offset into each frame. Type 0 is the frame's origin, 1 and 2 are later points. The handle
  block holds a count at +0 and a pointer to the title's own handles at +8, which are signalled
  with the event. Flag 1 takes the event off the clock. The title schedules type 0, then type 2,
  both at offset 0 and without handles.
* Slot 80, `WaitFrameEventX(type, timeout in ms, handle block, flags, token)`, waits for the next
  event of a type. A wait for the origin hands out a frame token, which slot 81
  (`GetFrameStatisticsX`) takes. Flag 2 hands out the token even when the wait times out.
* The results, as xcl reports them: slot 78 returns `S_FALSE`, slot 79 returns `0x10000000` when
  it starts the clock and `S_FALSE` otherwise, and a wait that times out returns `S_FALSE`. The
  title's call sites after slots 78 and 79 only test for success.

Ours (`runtime/gpu/frame_clock.h`) runs the clock on a thread of its own with a high-resolution
waitable timer, not locked to the display:

* Each event type has an auto-reset event set at each occurrence, which a wait waits on. A late
  clock signals once, for the latest occurrence, not once for every frame it missed. A new frame
  length restarts the frames from now.
* The title's handles are duplicated when the event is scheduled, so the clock can still signal
  them after the title closes its own, and set with `SetEvent`, or released if they are
  semaphores.
* Tokens are 48-bit and never 0; a wait hands one out only when the title passes 0.
* Not modelled yet, and logged once each: waits with a handle block (`E_NOTIMPL`), flags other
  than the two above, and slot 81. The periodicity and output arguments are logged and not
  used.

## Command lists write records inline

**Checked here** on `XboxBvhBuilder.dll` of 1.0.2.1, with REA and a disassembly sweep whose
output stayed in `private/`. It confirms what xcl reports.

Code built against the console headers doesn't always call a command list's methods. For common
commands it writes a record straight into a buffer that the list object points at, and calls the
method only when the buffer has no room. The builder does this at 205 places in 30 functions,
and every one follows the same steps:

1. Read the write pointer at +0x18 of the list object.
2. Compare it, unsigned, with an end pointer: +0x28 for dispatch records, +0x30 for the others.
3. If the pointer isn't below the end, call the list's method at a fixed vtable slot with the
   ordinary arguments, and write nothing.
4. Otherwise write the record and store the advanced pointer back at +0x18.

Two of the 205 compare with a copy of the +0x30 end held in a register across two records. No
store to the write pointer escapes a check: the builder's other stores to a +0x18 field belong
to unrelated structures (strings, allocators, zeroed blocks).

| Record | End | Sites | Size | Method when there's no room |
|---|---|---|---|---|
| Dispatch | +0x28 | 31 | 16 bytes: a header and three group counts | slot 14, `Dispatch`, as on desktop |
| Dispatch with a fourth word | +0x28 | 4 | 20 bytes | slot 80, console only |
| Pipeline state | +0x30 | 34 | 28 bytes | slot 25, `SetPipelineState`, as on desktop |
| One root constant | +0x30 | 36 | 8 bytes | slot 37, `SetComputeRoot32BitConstant` (desktop 33) |
| Several root constants | +0x30 | 16 | a header, then 4 bytes per constant | slot 39, `SetComputeRoot32BitConstants` (desktop 35) |
| Root view | +0x30 | 9 | 12 bytes: a header and a GPU address | slot 43 (desktop 39, the SRV setter) |
| Root view | +0x30 | 75 | 12 bytes | slot 45 (desktop 41, the UAV setter) |

Each method was matched by the arguments its call passes: three group counts for slot 14; an
index, a value and an offset for 37; an index, a count, a pointer and an offset for 39; an index
and an address for 43 and 45. The root signature setter has no inline form. The builder always
calls it, at slot 33 (desktop 29). So the compute root methods from desktop slot 29 to 41 all sit
four slots higher on the console. That fits Leonida's `SetDescriptorHeaps` at 32 (desktop 28).
Slots 43 and 45 take the same arguments, so their names rest on that shift alone.

The list object's fields that this code uses:

* +0x00, the vtable; +0x18, the write pointer; +0x28 and +0x30, the two ends.
* +0x140, +0x141 and +0x143, flag bytes. Root and pipeline state records set +0x140. A dispatch
  record picks its header from the three bytes and clears +0x140. Only the inline path touches
  them.
* From +0x344, one 32-bit word per root parameter: the header for that parameter's records,
  filled in when the root signature is set. When neither of its top two bits is set, writing the
  record also sets +0x140.
* +0x544 to +0x563. Before every pipeline state check, whatever its outcome, the code copies 32
  bytes here from +0x10 of the pipeline state object.

So the title also reads a pipeline state object's own memory: 32 bytes from +0x10 at every
`SetPipelineState`, and one bit of the word at +0x20 on the inline path.

**For `runtime/gpu`.** A list object whose write pointer is never below either end (for example,
all three zero) sends all 205 sites to its methods, which can then record onto a desktop command
list as usual. The object still has to be writable memory of at least 0x564 bytes, because of
the copy into +0x544 before the check. A pipeline state object needs at least 0x30 readable
bytes. In the builder, then, nothing writes command buffers behind the runtime's back. The main
executable may inline more kinds of record (draws, for instance) and needs the same check.

## Other list methods the builder calls

* Slot 26, once, with one legacy UAV barrier (type 2, no resource): `ResourceBarrier`, as on
  desktop.
* Slot 146, 29 times in 7 functions. 11 are direct calls through the vtable; the other 18 load
  the method into a register first, which an earlier count of 11 missed (Leonida counts 29). The
  direct calls pass one barrier group of type 0 (global) holding one barrier. Its sync words are
  0x80 and its access words 0x10, the public values for compute shading and unordered access. So
  slot 146 takes the arguments of the enhanced `Barrier` call, which is slot 80 on desktop.
* Slots 71 and 73, 7 times each, with a GPU address and further words. Every call sits behind
  two flag bytes in the builder's `.data`: the one at RVA 0xD773C must be nonzero and the one at
  0xD773B zero. Both are zero in the file, and no builder code writes them, takes their address,
  or holds a pointer to them, so the shipping builder never makes these calls. What the slots do
  doesn't matter for it.

The builder never calls slot 59 or 61. `amd_fidelityfx_upscaler_xbox.dll` does: it calls slot
61 with the arguments of `ExecuteIndirect` (a command signature, a maximum count, an argument
buffer and offset, and a count buffer and offset), and slot 59 with a flag, a data pointer and a
byte size, which isn't that shape. So `ExecuteIndirect` is slot 61, as Leonida has it, not 59 as
xcl reports.

## Descriptor copies

**Checked here** on `amd_fidelityfx_upscaler_xbox.dll`, after Leonida's report. Before it copies
one CBV, SRV or UAV descriptor between two CPU descriptor handles, the upscaler tests a byte at
+0x18 of the device object.

* When the byte is zero, it copies the 32 bytes itself, from one handle's address to the other.
* Otherwise it calls device slot 24, `CopyDescriptorsSimple` as on desktop, with one descriptor
  and heap type 0 (CBV, SRV and UAV).
* It gets the handle increment from slot 15, `GetDescriptorHandleIncrementSize` as on desktop.

**For `runtime/gpu`.** The device wrapper has to keep that byte nonzero, so every copy reaches
`CopyDescriptorsSimple` where it can be forwarded. With the byte at zero, the title would write
straight through desktop CPU handles, which point at driver memory it doesn't own.

## Reported by other projects

For `runtime/gpu` at M3; none of it is checked here yet ([related-work.md](related-work.md)).

* **Two runtime layouts** (xcl, on Unicorn Overlord). A newer console runtime reports the same
  SDK version, 0x20004, but moves slots. The queue has two more methods before `Signal`:
  `Signal` is 16, `Wait` 17, `GetTimestampFrequency` 18, `SignalX` 25 and `PresentX` 32, where
  the older layout has 14, 15, 16, 23 and 30. On the command list, the console methods from
  `CopyTextureRegionX` on sit two slots later, 83 to 94 becoming 85 to 96; where the shift
  starts below 83 isn't known. The device is unchanged. xcl tells them apart by a fence passed
  to queue slot 16 or 17. The list slots above come from the side DLLs; the executable's queue
  calls will show which layout it was built against.
  * Queue slot 18 differs too (xcl, `a01d61c`). In the older layout it is `GetDesc`, which
    returns a 16-byte description through a hidden return pointer; in the newer layout it is
    `GetTimestampFrequency`, which returns 8 bytes. A title can call it before its first
    `Signal`, which is before the fence test above can tell the layouts apart.
* **`D3D12XboxCreateDevice`.** Xbox2Windows' shim refuses a non-null parameter block and any
  interface other than `ID3D12Device`, then creates a desktop device at feature level 12.0.
  That is its assumption. Leonida reports a 24-word parameter block, so a title that passes one
  needs the block read, not refused.
* **Resource creation** (xcl, on Fortnite, Unicorn Overlord and Minecraft):
  * A committed console resource that isn't placed needs a desktop description, with the
    driver's alignment and layout and the console's flag bits cleared, or creation fails with
    `E_INVALIDARG`.
  * The console-only state bit 0x100000, seen on a 4K display target, has to be masked.
  * A texture can take more memory on desktop than its console size.
* **Unified memory and `memory_tracker`** (xcl, measured on XDefiant):
  * A title's first graphics reservation can be 8 GiB + 4 MiB.
  * A write-watch scan over about 2 GB at every submission costs about 0.8 ms, at about 800
    submissions a second.
  * Only the 64-byte chunks the CPU changed may be uploaded: the rest of a page can hold
    counters or indirect arguments the GPU wrote.
  * Making cold pages read-only makes `ReadFile` into title memory fail rather than fault.
    Overlapped or unbuffered reads may bypass write-watch (an assumption).
  * Titles fill vertex rings after recording a draw, so the sync happens at
    `ExecuteCommandLists`, not while recording.
  * Console address 0 reads as null, so the first 64 KiB stays unused, and the 32-bit
    descriptor range stays out of title reservations.
  * xcl now keeps title graphics memory in 4 GiB reserved buffers whose tiles are mapped as
    memory is committed, plus a 512 MB coherent window for readback. The GPU copies data back
    to the CPU only for a list's memory writes and for `Map` with a read range.
  * **Video-memory arenas** (xcl, `70d7e0a`, on XDefiant): a later placement can straddle an
    existing arena, about 78 s in. Each title address has to map to one backing heap, or
    aliasing breaks, so xcl merges overlapping arenas into their union.
* **Write-watch limits** (xbox-emulator): views of physical pages or file mappings can't carry
  write-watch, and on its Windows build the first read of a page never touched marks it dirty.
* **Command list `Reset`** (xcl, `c806a0b`): call the native `Reset` first, and drop the
  per-recording state the wrapper tracks only if it succeeds.
* **Frame clock** (xcl, `23c53fc`): with two or three frames in flight, the frame statistics
  for a token have to carry that frame's own origin time. Extra handles signalled outside the
  clock's lock have to stay open after the frame event is rescheduled.
* **Memory windows in translated shaders** (xcl, `a787c52`, reverted in `70f8dc4`; `07f12e8`;
  `3304bb1`):
  * Picking a window from a 64-bit address has to include the carry out of the low dword. xcl
    reverted that fix because `amdxc64.dll` crashed on one 2,552-instruction compute shader.
  * The window choice has to be a `select()`: in HLSL 2021 `?:` short-circuits into a branch
    (see "Branches in generated HLSL" in [shaders.md](shaders.md)).
  * Switching windows once per four dwords cut DXC's CPU time from 771 to 424 s over 253
    programs.
  * Mesh and geometry programs need the same windows.
* **DXC cost** (xcl, `56fa1dc`; see also "Pipeline compile time" in [shaders.md](shaders.md)):
  * Programs translated with program-counter loops, 13% to 17% of them, take 53% to 75% of the
    compile time.
  * `-O0` saves about a third.
  * DXC peaks at 0.6 to 0.7 GB per compile.
  * Compile workers stay at normal priority, since game threads wait on pipelines.
* **Start-up GPU check** (xcl, `8ba374c`): shader model 6.6, the mesh shader tier, the wave
  width, and DXC. A GPU with 8 to 16 lanes can run neither form of a wave64 program, native or
  split into 32-lane halves (see "Wave size" under the host constraints in
  [shaders.md](shaders.md)).
* **Windows 10 and 11 differences** (Leonida, `0e1ecbb8`): Windows 10's `d3d12.dll` has no
  `ID3D12Device10`. The in-box WARP of Windows 11 23H2 reports `RelaxedFormatCastingSupported`
  as 0, and `CreateCommittedResource3` with castable formats fails there. So cast views need a
  fallback.
* **GPU tests without a desktop** (Leonida, `55200be1`): over SSH or as a service, DXGI returns
  `DXGI_ERROR_NOT_CURRENTLY_AVAILABLE` for `EnumOutputs` and `CreateSwapChainForHwnd`. GPU tests
  should skip there.
